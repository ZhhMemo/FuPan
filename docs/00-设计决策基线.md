## 0. 项目命名

**主名：复盘**（fù pán）

用户拍板改名。「复盘」在 A 股语境里是现成的高频词，任何投资者一听就懂——
把走过的行情重新走一遍，看当时的决策对不对。定位和名字完全贴合，
**不需要任何解释成本**，这是它最大的优势。

- 一句话定位：**一组区间，一次判断，一个真实结果。**

备选：**温故**（原定名）、**重演**、**知往**。

## 2. 区间定义：两方案评估

你提的两个方案我都评估了，结论是**都不单独用，做混合**。理由如下。

### 方案 A：算法自动识别

用规则或统计方法在历史 K 线上切分区间。可用手段：

| 方法 | 切出什么 | 成熟度 |
|---|---|---|
| ZigZag / 波峰波谷 | 趋势段（上涨/下跌/震荡） | 高，一天可写完 |
| 均线系统交叉 | 多空转换段 | 高 |
| ADX / 波动率聚类 | 高波动段 / 低波动段 | 中 |
| HMM 状态划分 | 上涨态/震荡态/下跌态 | 中，需调参 |
| 事件驱动 | 财报、除权、解禁、涨跌停、停复牌 | 高 |
| 形态识别 | 箱体、突破、缺口、双底双顶 | 中 |

**优点**

- **确定性**：同一只股票、同一参数，每次跑出的区间完全一致。这对学习平台至关重要——今天练的题和昨天练的题必须是同一道题。
- **速度**：毫秒到秒级，可以全市场批量预生成，题目池随时有货。
- **零成本**：不烧 token，可以无限次重跑调参。
- **可评估**：可以量化「这个切分参数好不好」。

**缺点**

- 只能识别**预先定义好**的模式，无法理解「为什么这段值得练」。
- 参数敏感，ZigZag 阈值从 5% 改到 8%，题就全变了。
- 生成的题目没有「人话描述」，用户面对的可能只是一段孤零零的 K 线。

### 方案 B：AI 出题

把股票数据交给 LLM，让它挑出有教学价值的区间并出题。

**优点**

- **灵活**：能识别语义层面的「好题」——比如「业绩预告下修 + 放量破位」这种算法很难表达的组合。
- **会说话**：能生成题目描述、考察点、当时的市场背景，用户体验好得多。
- **能造干扰项**：可以生成「相似但结局相反」的对照区间，教学价值高。

**缺点与风险（必须正视）**

| 风险 | 说明 | 严重度 |
|---|---|---|
| **幻觉** | 会编造当时不存在的财报数字、公告内容，直接污染题目 | 高 |
| **不可复现** | 同样输入两次结果不同，题目集合不稳定，学习进度无法累积 | 高 |
| **模型侧前视** | 模型训练数据里可能已包含这段行情（如「2024 年 2 月大反弹」），它会不自觉地把答案泄出来 | **严重** |
| **上下文限制** | 塞不下长序列，必须先把 K 线压缩成摘要文本，信息有损 | 中 |
| **成本与延迟** | 全市场预生成不现实；按需生成几秒到几十秒，影响体验 | 中 |

其中**模型侧前视**是最隐蔽也最致命的：你以为没给模型未来数据，但模型可能「记得」那段历史。
这类偏差无法完全消除，只能通过**限制模型的职责**来降低影响。

### 结论：混合方案（A 主干 + B 增强）

> **算法负责「切」，AI 负责「选」和「说」。**

分工：

1. **算法层**：先在全历史上，用固定参数把所有候选区间切出来，存入题目池。
   → 边界精确、可复现、零成本。
2. **AI 层**：从候选池里挑选教学价值最高的 N 个，生成题目描述、考察点、难度分。
   → AI 只做**排序和叙述**，不做边界判断。

这样做的关键收益：

- 区间边界由算法保证，**AI 不参与边界计算**，从结构上杜绝了「模型把边界挪到对自己有利的位置」。
- 即使 AI 输出有幻觉，最坏情况只是题目描述写得不对，**不影响结算结果**（结算只用数值数据）。
- AI 调用可以离线批处理，不阻塞用户操作。
- AI 不可用时，系统退化为纯算法模式，**功能降级但不失效**。

**AI 调用的硬约束**

- 输入必须是**脱敏摘要**：只给区间内及之前的数据统计量 + 一个内部编号，绝不给区间后的数据。
- 输入中**不含股票名称和真实日期**，只用编号和时间偏移（如「第 0 日 ~ 第 60 日」）。
  → 大幅降低模型「认出这段行情」的概率。
- 强制输出结构化 JSON，字段缺一即丢弃该题。

## 3. 区间类型标签体系

每道题必须带一个类型标签，这样学习档案才能看出「你在哪类行情上判断得准」。

| 标签 | 说明 |
|---|---|
| 趋势延续 | 已在上升趋势中，判断是否继续 |
| 趋势反转 | 拐点附近，判断是否转向 |
| 横盘突破 | 长期缩量整理后的方向选择 |
| 横盘破位 | 支撑失守 |
| 高位放量 | 涨幅已大，成交量异常放大 |
| 缩量回调 | 上涨途中的缩量回调 |
| 事件驱动 | 财报、重组、解禁、并购 |
| 极端行情 | 千股跌停、指数熔断、暴涨暴跌 |

## 4. 题目数据结构（统一 Schema）

算法和 AI **必须输出同一个结构**，这样下游结算逻辑只需要写一遍。

```
question
├── question_id        题目唯一 ID（可复现，由股票+区间+参数哈希生成）
├── code               股票代码
├── start_date         区间起始日
├── end_date           区间结束日（= 决策点 T）
├── pattern_tag        区间类型标签（见第 3 节）
├── position_type      题型：empty（空仓型）/ holding（持仓型）   ← 2026-09-16 新增
├── initial_position   初始持仓快照：{shares, avg_cost}（空仓型为 null）  ← 新增
├── initial_cash       初始可用资金（默认 10 万元）
├── source             来源：algorithm / ai / hybrid
├── visible_until      数据可见截止日（恒等于 end_date）
├── settle_window      结算窗口（交易日数）
├── settle_params      结算参数（费率 / 滑点版本）← 用于快照冻结
├── title              题目标题（AI 生成，算法模式可为空）
├── description        题目描述（AI 生成，算法模式可为空）
├── key_points         考察点列表（AI 生成）
├── difficulty         难度分 1-5（不向用户展示）
└── created_at         生成时间
```

**两个必须注意的点**：

1. **`question_id` 由哈希生成**：只要股票、区间、**初始持仓**、参数不变，ID 就不变。
   这是「同一道题可以反复练、可以对比进步」的技术基础。
2. **`initial_position` 是 2026-09-16 改为下单制后新增的字段**。
   题目必须能表达「你已持有 N 股、成本 Y」这种状态——
   否则「该不该卖」这类最有价值的训练场景无从谈起（见第 5.2 节）。

## 5. 决策方式：真实下单，不是选择题

### 5.1 决策从「三选一」改为「下单」

**2026-09-16 修订**：原设计让用户在「买入 / 持有 / 卖出」中三选一。
现在改为：**用户实际下单**（买 / 卖 + 股数），系统按真实规则成交并结算。

理由不只是「更真实」，还顺手解决了一个原设计的硬伤：

> 「持有」和「卖出」在**无仓位**前提下执行结果完全一样
> （都是不建仓、策略收益都是 0%），只是名字不同。
> 原设计一直没解释清：那为什么还要区分它们？

有了真实仓位，这个歧义**自动消失**——有仓位时，「持有」和「卖出」是完全不同的动作。

### 5.2 题目有两种初始状态

每道题必须指定初始持仓，**两种题型都要有**：

| 题型 | 初始状态 | 训练什么 |
|---|---|---|
| **空仓型** | 现金 100%，无持仓 | 「这个位置该不该进场、进多少」 |
| **持仓型** | 已持有 N 股、成本 Y | 「该加仓、减仓、清仓，还是不动」 |

**为什么持仓型更重要**：真实交易中你绝大多数时间是**已有持仓**的。
「该不该卖」往往比「该不该买」更难。原设计只覆盖了空仓型。

两种题型建议按比例混合（初始可五五开），题目上打标签，便于分开统计。

### 5.3 用户能做哪些操作

| 操作 | 说明 |
|---|---|
| 买入 | 指定股数或金额 |
| 卖出 | 指定股数（不超过可卖数量） |
| 不动 | 有仓位即「持有」，无仓位即「观望」 |

同时提供快捷按钮（空仓 / 半仓 / 全仓 / 清仓）降低操作成本。

**「买多少」本身就是训练内容**——仓位管理是原三选一设计完全丢失的维度。

### 5.4 判卷模式

系统给出**仓位建议**（例如「建议加仓至 60%」），用户评判这个建议对不对，再走结算。
比原来的「买 / 持 / 卖」判断更具体，对新用户也更友好——
不需要自己先有观点，只需要会评判。

### 5.5 与回放模式的边界

两个模式**共用同一个交易引擎**，区别只在**推进粒度**：

| | 判断模式 | 回放模式 |
|---|---|---|
| 决策点数量 | **一个**（区间末） | 每推进一格都可决策 |
| 推进粒度 | 整个区间 | 5 分钟（可配） |
| 单次耗时 | 30 秒 | 数分钟到数小时 |
| 定位 | 题海式快练 | 沉浸式实战 |

> ⚠️ **待确认**：是否允许在结算窗口内设置多个决策点？
> 若允许，判断模式就变成「日线粒度的回放模式」，两者边界会模糊。需明确后再定。

## 6. 结算规则

### 6.1 默认参数（两个模式通用）

| 参数 | 默认值 | 可选范围 |
|---|---|---|
| 决策点 T | 区间最后一个交易日 | — |
| 成交时点 | T+1 日**开盘价** | 可选 T+1 收盘价 / T 日收盘价 |
| 结算窗口 | **20 个交易日**（约一个月） | 5 / 10 / 20 / 60 / 120 / 自定义 |
| 平仓时点 | 第 20 个交易日**收盘价** | 可选 |
| 初始资金 | 10 万元 | 自定义 |
| 基准指数 | **沪深300（000300）** | 可加：上证、创业板指、中证500 |
| 滑点 | 双向各 **0.05%** | 自定义 0 ~ 0.5% |
| 佣金 | **万分之 2.5，最低 5 元** | 万1 ~ 万3 |
| 印花税 | 卖出单边 **0.05%** | 政策固定 |
| 过户费 | 双向 **0.001%** | 政策固定 |
| 规费 | 含在佣金内（全佣模式） | 可切换「净佣 + 规费单列」 |

> 费率依据 2026 年现行标准：印花税 0.05% 卖出单边（2023 年 8 月起减半）、
> 过户费 0.001% 双向（沪深统一）、佣金万 1~万 3 最低 5 元、规费合计 0.0541‰ 双向。
> 这三项会随政策调整，**应做成可配置参数而非硬编码**。

### 6.2 自定义与自动计算

- **用户自定义**：以上所有参数都允许覆盖，形成「我的交易设定」，练习时统一生效。
- **算法自动计算**：结算本身是纯确定性计算，不需要 AI。
- **AI 自动计算**：用于**解释结算结果**——为什么这笔交易亏了、当时最大的风险信号是什么。
  即 AI 负责「归因叙事」，不负责「算数字」。数字必须由算法算，AI 只解读。

### 6.3 下单的结算语义

**2026-09-16 修订**：原设计是「买入 / 持有 / 卖出」三选一，现已改为**真实下单**。

原来的三选一有一个硬伤：在**无仓位**前提下，「持有」和「卖出」的执行动作
完全一样（都不建仓、收益都是 0%），只是名字不同，无法解释为什么要区分。

改为下单后，语义变得清晰：

| 操作 | 有仓位时 | 无仓位时 |
|---|---|---|
| **买入** | 加仓 | 建仓 |
| **卖出** | 减仓 / 清仓 | 不可执行（无可用份额） |
| **不动** | 持有 | 观望 |

每种操作的结算都由**交易引擎**按真实规则执行（见 `03-时间回放模式设计.md` 8.1），
结果统一落到**账户视角**（总资产 = 现金 + 持仓市值）。

**关键设计**：无论用户如何操作，每次都**额外记录「机会成本」**——
如果决策点全额买入会怎样。否则用户会发现「只要一直不买，大盘跌的时候
我的收益率就是 0%，永远跑赢沪深300」，然后学会一个完全错误的策略。

### 6.4 输出指标（不判对错）

**不定义成功/失败**，每次练习输出一组事实：

| 指标 | 含义 |
|---|---|
| **账户收益率** | (期末总资产 − 初始总资产) / 初始总资产，含全部成本 |
| 标的收益率 | 该股票在结算窗口的实际涨跌 |
| 基准收益率 | 沪深300 同期 |
| 超额收益 | 账户收益率 − 基准收益率 |
| **机会成本** | 标的收益率 − 账户收益率（错过了多少 / 躲过了多少） |
| 最大回撤 | 持有期间的最深浮亏 |
| 全程持有对照 | 若决策点买入并持有到底的收益 |

「机会成本」和「超额收益」配对出现，才能防止「一直不买」造成的自我误判。

## 7. 成交可行性规则

目标是「尽可能接近真实炒股」，以下规则必须实现。

| # | 规则 | 处理方式 |
|---|---|---|
| 1 | **T+1** | 当日买入当日不可卖。所有卖出信号顺延一个交易日 |
| 2 | **一字涨停** | 当日 `最高价 == 最低价 == 涨停价` → 禁止买入，顺延到下一个可成交日 |
| 3 | **一字跌停** | 同理 → 禁止卖出，顺延 |
| 4 | **开盘即封板** | `开盘价 == 涨停价` → 视为无法买入（保守规则，可配置开关） |
| 5 | **停牌** | 停牌期间禁止交易，顺延至复牌首日 |
| 6 | **新股前 5 日** | 注册制股票上市前 5 日无涨跌幅限制。**直接从标的池剔除上市不足 60 个交易日的股票**，回避复杂度 → **因此无需特判首日** |
| 7 | **ST 股** | **MVP 不做 ±5% 特判，改为从标的池剔除 ST**。⚠️ 但 `is_st` 目前靠证券名称含 "ST" 判定，**不可靠**；M2 建时点标的池时应改用 `query_all_stock(day=...)` 的**当日名称快照**（point-in-time）重做 |
| 8 | **涨跌幅比例（须按日期分段）** | ⚠️ **原设计漏了日期分段，会导致历史回测的涨跌停价算错**：<br>· 主板 ±10%（自 1996-12-16 起）<br>· **创业板（sz.30x）：2020-08-24 起 ±20%，之前 ±10%**<br>· 科创板（sh.688）：2019-07-22 开板起即 ±20%<br>· 北交所：2021-11-15 开市起 ±30% |
| 9 | **退市整理期** | 退市整理期涨跌幅按 **10%** 处理（与板块常规不同）。**推断方式为近似**：以 `delist_date` 往前推 30 个交易日；真实起止需交易公告，数据源拿不到 |
| 10 | **价格精度** | 涨跌停价四舍五入到分（HALF_UP），与真实规则一致 |
| 11 | **流动性上限** | 单笔成交量 ≤ 当日成交量的 1%（小资金可忽略，预留字段） |

**成交价假设**：默认「T+1 开盘价 + 滑点」。这是最接近真实散户的假设，
比「收盘价成交」严格，比「理想价成交」诚实。

## 8. 复权处理

你说不太懂这块，我按真实情况给出方案。先讲清楚是什么。

### 8.1 什么是复权

股票分红、送股、配股后，股价会**凭空跳空**。比如 10 派 5 元，除权日股价直接少 0.5 元——
但这不是下跌，是你账户里多了现金。如果直接用真实成交价看历史，会看到一堆假的「暴跌」。

复权就是把这种跳空还原掉的技术。

### 8.2 三种价格的区别

| 类型 | 基准 | 历史价会不会变 | 价格量级 | 适合 |
|---|---|---|---|---|
| **不复权** | 真实成交价 | 不变 | 真实 | 看真实盘面、算成本 |
| **前复权** | 以**最新价**为基准往前调整 | **会变**（每次新除权都重算全部历史） | 贴合当前价 | **界面展示** |
| **后复权** | 以**上市首日**为基准往后调整 | 不变 | 明显偏大（茅台可达上万） | **算收益率、回测** |

### 8.3 本项目的决策

> **存储存「不复权 OHLCV + 复权因子」；展示与计算按训练模式分别取用。**

| 场景 | 用什么价 | 为什么 |
|---|---|---|
| **判断模式 · 界面展示** | 前复权 | 用户的心理预期是「价格和同花顺一致」，量级也对得上 |
| **判断模式 · 结算** | 后复权 | 分红送股后股数变了，不复权算出的收益率是错的 |
| **回放模式 · 展示与成交** | **不复权** | 回放是把时间推回某一天，用户看到的必须是**当时的真实报价**。前复权的基准是「最新价」，历史价会被后续分红全部改写，与当天盘面对不上 |
| **回放模式 · 收益** | **不复权价 + 现金分红流水** | 回放里有真实持仓，分红应作为**现金入账**、送股应**调整股数**，不能简单套用后复权 |

**存储为什么只存一套**：

1. 只存一套原始数据，各种口径都能现算，省空间且永不失真。这是行业标准做法。
2. **前复权的历史会变**——今天存的前复权数据，明天公司除权后就错了。
   所以前复权必须**实时计算，不能落库**。
3. 后复权同理：新的除权会改变**全部**历史的后复权价，也不能落库。

> ⚠️ **修订说明（v0.6）**：原决策写的是「展示用前复权，计算用后复权」，**没有区分训练模式**。
> 这会让回放模式在除权日**凭空出现巨大亏损**——送股让股数变了、分红让现金多了，
> 而引擎完全不知道。已在 `03-时间回放模式设计.md` 补上「除权除息处理」一节。

### 8.4 分红的简化

真实情况下，分红会给你现金（还涉及红利税），复权处理「分红再投资」——
等价于分红自动按除权价买入更多股票。

- **本项目决策**：默认用**后复权价**计算，即等价于「分红全部再投资」。
- 这是简化，但对学习平台是合理的（差额很小，且逻辑自洽）。
- 后续如果要更真实，可以单独建模现金分红流水，作为 V2 的增强项。

## 9. 前视偏差防火墙

这是整个产品的**成败关键**，必须做，且必须做在后端。

**核心原则：用户和 AI，在任何环节都不能拿到决策点之后的数据。**

落地方式：

1. **数据出口收敛**：所有对外接口的数据，统一经过一个 `mask(date > visible_until)` 过滤器。
   不允许任何接口绕过它。
2. **不在前端隐藏，而在后端不返回**。前端「不渲染」等于没做——数据已经在客户端了。
3. **结算接口单列**：结算必须由一个独立接口触发，且只在用户提交判断后才允许调用。
   防止用户抓包提前看到结果。
4. **AI 侧同样隔离**：喂给模型的输入必须是脱敏摘要，不含真实日期与股票名（见第 2 节）。
5. **题目池预生成时**：算法切分天然不会用到未来数据（只做局部窗口计算），但要注意
   **归一化/标准化的统计量不能在全历史上计算**（比如用全历史均值标准化某一天的量，
   就等于泄题）。所有滚动指标必须严格用「截止当日」的窗口。
6. **指标线必须截断在决策点**：均线 / MACD / KDJ / BOLL 由历史数据算出，本身不含未来信息，
   所以作答中开放它们是安全的。但**绝不允许把指标线画到决策点之后**——哪怕只是一段
   延伸线，也会把后续走势的形状暴露出来。渲染层必须 `mask(<= visible_until)`。
7. **显著性打分不得使用决策点之后的数据**：知识复盘模块的 `confirmation` 特征
   必须定义为「决策点**前**的确认度」，不能写成「形态被后续 K 线确认」（见 12.5）。

 第 5 点是新手最容易踩的坑，也是最容易被忽略的：**技术指标本身可能带着未来信息**。
 第 6、7 点本项目的具体落地点，实现时极容易被当成"细节"漏掉，务必写进验收清单。

## 10. 幸存者偏差（回答你的疑问）

**你的问题：退市股要留在历史里？这是什么意思？**

### 10.1 一句话解释

如果你只用**今天还在上市**的股票去做练习和统计，你就自动排除了所有
「曾经存在过、但后来暴雷退市」的股票。结果是你看到的胜率**天然被高估**，
因为你眼里只有活下来的赢家。

### 10.2 经典类比

二战时统计返航飞机的弹孔分布，发现机翼上弹孔最多、发动机上几乎没有。
有人提议加固机翼。正确答案是**加固发动机**——
因为发动机中弹的飞机根本没能飞回来，所以不在统计样本里。

**你看不到的部分，才是决定结论的部分。**

### 10.3 落到本项目

如果数据库里只有当前在市的大约 5400 只股票：

- 用户随机抽题，**永远抽不到**乐视网、康美药业这类「退市前最后一段」的区间。
- 用户会形成「跌了总会涨回来」的错误经验——因为在他们的样本里，跌下去的确实都涨回来了。
- 学习档案里的胜率会系统性偏乐观，从而**误导学习方向**。

### 10.4 处理方案

| # | 措施 | 说明 |
|---|---|---|
| 1 | **数据源必须含退市股完整历史** | Baostock 明确支持退市股完整历史（已核实），这是选它的重要原因 |
| 2 | **构造「当时在市」的标的池** | 出题时，用「该交易日当时在市的股票」作为池子，而不是「今天在市」的股票 |
| 3 | **保留退市前的最后一段** | 退市整理期的行情也要保留，否则结算时股票会「凭空消失」 |
| 4 | **退市结算规则** | 若结算窗口内股票退市，**取「最后一个可成交交易日」的收盘价强制平仓**，并标记该题。<br>⚠️ **2026-09-16 实测修正**：必须取 `fact_daily.is_trade = True` 的**最后一行**，**不能用 `MAX(date)`**——实测乐视退（sz.300104）退市日 2020-07-21 当天 `tradestatus='0'`、**无成交量、不可成交**，真正最后的可成交日是 2020-07-20（收盘 0.18）。部分股票（如邯郸钢铁换股合并）退市前还长期停牌 |
| 5 | **保留 dim_stock 的上市/退市日期字段** | 这是实现 point-in-time 标的池的基础字段 |
| 6 | **保留 `fact_daily.is_trade`** | 上面第 4 条依赖它。这个字段不是可选项 |

第 2 条里的术语叫 **point-in-time universe（时点标的池）**——
它要求你回答「2020 年 3 月 2 日那天，A 股在市的股票有哪些」，
而不是「今天的 A 股有哪些」。这是所有严肃回测的基础设施。

## 11. 数据源与存储

### 11.1 数据源选型（免费方案）

| 数据源 | 用途 | 理由 |
|---|---|---|
| **Baostock**（主） | 日线 OHLCV、复权因子、交易日历、指数 | 免费无需积分、无流量限制、历史极深、**含退市股** |
| **AkShare**（补充） | 财务数据、公告、板块、龙虎榜 | 接口极丰富，但属爬虫，易失效，**只做按需补充** |
| Tushare（备用） | 校验、兜底 | 免费积分档够校验用 |
| 巨潮资讯（后期） | 公告财报原文 | 基本面题目的素材来源 |

**关于 AkShare 的注意事项**：它是爬虫，接口会随上游网站改版失效，
**绝不能用它做 7×24 的定时任务**。定位为「临时查数据 / 补充字段」。

**Baostock 的注意事项**：数据是盘后更新，无实时行情。
本项目是历史数据学习平台，**不需要实时行情**，所以完全够用。

**关于分钟级数据（时间回放模式依赖，见第 15 节）**

| 粒度 | 来源 | 历史范围 |
|---|---|---|
| 5 / 15 / 30 / 60 分钟 | **Baostock** | **1999-07-26 至今**，深度足够 |
| 1 分钟 | Baostock **无**；AkShare 有接口但历史深度浅 | ⚠️ 只能做近日训练 |

指数**没有**分钟级数据，所以回放模式里的沪深300 基准只能用日线。

**数据更新时间（据 Baostock 官方说明）**

| 数据 | 入库时间 |
|---|---|
| 日 K 线 | 当日 **17:30** |
| 分钟 K 线 | 当日 **20:30** |
| 财务数据 | 次日 1:30 |

> ⚠️ 上面这张表**推翻了原定的 16:00 同步时间**：16:00 时当日数据根本还没入库，
> 同步会拉不到当天数据。**同步时间已调整为 21:00。**

### 11.2 存储决策：DuckDB + Parquet

**结论：DuckDB（查询引擎）+ Parquet（列存文件格式）。**

| 候选 | 评价 |
|---|---|
| **DuckDB + Parquet** ✅ | 单文件、零运维、列存+向量化、毫秒级查询、与 Python/Pandas 无缝、SQL 兼容度高 |
| SQLite | 行存，4000 万行聚合查询偏慢；也够用，但没优势 |
| PostgreSQL | 要装服务、要运维，个人项目过重 |
| ClickHouse | 性能最强但要运维，杀鸡用牛刀 |

**理由**：

- **不需要装数据库服务**。一个文件，随项目走，本地起停即用。
- **列存 + 向量化**非常适合「按日期区间扫某只股票」这个核心访问模式。
- Parquet 压缩率高，全历史数据能压到几百 MB 级别。
- 将来要迁 PostgreSQL / ClickHouse，SQL 基本不用改。

### 11.3 数据规模估算

- 全 A 股约 5400 只（含退市约 6000+）
- 每只约 30 年 × 250 个交易日 ≈ 7500 行
- 合计约 **4000 万 ~ 4500 万行**
- 每行约 60 字节 → 原始约 2.5 GB → **Parquet 压缩后约 300 ~ 800 MB**

**结论：单机完全 hold 得住，不需要任何分布式方案。**

### 11.4 数据分层

```
raw/    原始落地层 —— 从数据源抓下来的原样数据，不修改
clean/  清洗层     —— 统一 schema、统一复权因子、补齐日历
app/    应用层     —— 题目池、下单记录、结算结果、回放会话
```

原始层永不修改，清洗层可随时从原始层重跑。这是数据工程的基本纪律。

- `dim_stock.delist_date` —— 构造 point-in-time 标的池的前提。
- `fact_daily.adj_factor` —— 让各种复权口径可以随时现算。
- `fact_order.params_snapshot` —— 记录下单当时的费率和复权因子版本，
  用于**结算快照冻结**（保证历史成绩日后重算不变）。

### 11.6 更新策略

- **历史全量**：首次一次性拉取，落 Parquet。
  分钟数据是**天级任务**（约 40 ~ 200 小时），**必须支持断点续传**
- **每日增量**：每交易日 **21:00** 自动同步
  （Baostock 日 K 17:30、分钟 K 20:30 才入库，早于此时段拉不到当天数据）
- **失败重试**：单只股票失败不影响整体，记录失败清单次日重试
- **数据校验**：每日同步后**自动**校验「股票数 / 日期连续性 / 价格非负非零 / 涨跌幅超限」，
  异常告警（对应 FR-7.1，P0 级）
- **时区**：定时任务必须**显式指定北京时间**，不能依赖服务器本地时区

## 12. 知识复盘模块（技术知识学习）

需求：在预测过程中学习技术知识（K 线形态、量价关系等），并支持关闭 / 开启。

### 12.1 定位：为什么叫「复盘」而不是「随行」

第一版设计叫「知识随行」，试图在作答**过程中**穿插教学。用户拍板后改为：

> **作答前不展示任何知识点；作答后，当算法匹配出本区间出现过的知识点时，
> 自动弹出供巩固记忆。**

模块定位因此从「过程教学」变成「**结果复盘式教学**」——
先让你独立判断，再告诉你刚才那段行情里其实发生了什么。名字随之改为**知识复盘**。

这个改动带来一个意外收益：**泄题风险归零，设计反而更简单。**

原方案里最脆弱的一环是「作答前展示 3~5 个候选知识点」——为了不让用户
靠数方向蒙答案，不得不加「方向配平」补丁。现在作答前什么都不给，
**配平机制整节作废**，实现量少一块，风险也归零。

### 12.2 三阶段设计

| 阶段 | 定位 | 提供 | 禁止 |
|---|---|---|---|
| **作答前** | 什么都不给 | 无 | **界面不出现任何知识点**、任何形态标注、任何信号提示 |
| **作答中** | 给工具，不给结论 | 默认开启的技术工具：均线、成交量、MACD、KDJ、BOLL；区间统计摘要（涨跌幅、振幅、量能变化）；自由缩放量取 | 不自动提示指标信号（如「MACD 金叉」）；不自动标注形态；**指标线不得延伸到决策点之后** |
| **作答后** | 揭晓 + 巩固 | 本区间匹配到的**全部**知识点（分层展示）；K 线图上高亮每次出现的位置；量价画像；该知识点的全历史实证统计；关联知识点 | 无（答案已揭晓） |

一句话原则：**作答前一个知识点都不给，作答后一次给足。**

> 为什么作答中可以开放技术工具：均线 / MACD / KDJ / BOLL 全部由**历史数据**算出，
> 本身不含未来信息，不构成泄题。它们的作用是把用户从「手工算数」中解放出来，
> 让精力集中在判断上。**前提是严格截断**（见第 9 节硬约束）。

### 12.3 匹配引擎

统一的检测器抽象：

```
Detector.detect(ohlcv_slice) -> List[Occurrence]

Occurrence = { kb_id, start_idx, end_idx, confidence, detail }
```

按 `detect_type` 分两路实现，对应形态的两种本质：

| 类型 | 适用知识点 | 检测方式 |
|---|---|---|
| **point**（点状） | 单根 K 线、K 线组合、部分指标信号 | 逐根 K 线滑窗，以候选点为中心取固定回溯窗口判定。局部计算，天然无前视 |
| **persistent**（持续） | 趋势结构、量价背离、均线排列、指标状态 | 在整段区间做序列 / 状态计算，返回「成立区间」而非单点 |

category 路由到具体实现，外层对结果统一打分排序。

### 12.4 一个知识点出现多次怎么处理

用户明确要求：**不人为限制成一个区间只保留一个同类知识点，按实际情况来。**

| 层 | 处理 |
|---|---|
| **数据层** | **存多条**，一次出现一条记录。不合并计数——每次出现的位置、显著性分、上下文都不同 |
| **展示层** | 按知识点聚合，标注「出现 N 次」；每次出现的位置在 K 线图上分别高亮；可展开查看逐次明细 |

例：区间内出现 3 次早晨之星 → 卡片显示「早晨之星 ×3」，展开后列出第 12 / 34 / 56 日
及各自显著性分。

### 12.5 显著性打分（分层展示的依据）

一个震荡区间可能命中 30 个以上知识点，全平铺会淹没用户。
所以**数据层全部保留、不设数量上限，展示层收敛**。

打分公式（**可解释规则，不引入需要训练数据的模型**）：

```
score = Σ(权重 × 特征)

strictness          命中条件数 / 条件总数     判定越严格越可信
confirmation        决策点前的确认度          形态在决策点前被验证的程度
position            距决策点的距离            越近越相关
duration            持续天数                  对 persistent 类生效
direction_clarity   方向明确度                非中性加分
```

展示规则：

- 按 score 降序，**默认展开前约 40%**
- 其余收进「查看全部」，按 category 分组
- **不设数量硬上限**——有多少展示多少，只是默认收起

> ⚠️ **硬约束**：`confirmation` 必须使用**决策点之前的确认度**。
> 若写成「形态被后续 K 线确认」，窗口一旦越过决策点就是前视偏差。

### 12.6 知识点知识库

```
dim_knowledge
├── kb_id             知识 ID
├── name              名称（如「早晨之星」）
├── alias             别名
├── category          分类
├── definition        一句话定义
├── detect_rule       可量化的识别规则      ← 关键字段
├── detect_type       point / persistent     ← 新增
├── window_size       判定窗口长度           ← 新增
├── min_confirm_bars  最少确认根数           ← 新增
├── base_weight       基础权重               ← 新增
├── sample_min        统计最小样本量         ← 新增
├── signal_direction  方向：bullish / bearish / neutral
├── position          常见位置：顶部 / 底部 / 中继
├── meaning           含义与用法
├── pitfalls          常见误用
├── diagram           示意图
└── related           相关知识点 ID
```

**分类体系**（覆盖你说的 K 线形态、量价关系，并留好扩展位）：

| 类别 | 示例 |
|---|---|
| 单根 K 线 | 大阳线、大阴线、十字星、锤子线、上吊线、T 字线 |
| K 线组合 | 早晨之星、黄昏之星、红三兵、三只乌鸦、吞没、孕线、缺口 |
| 趋势与结构 | 趋势线、支撑阻力、箱体、三角形、旗形、头肩顶底、双底双顶 |
| **量价关系** | 量增价升、量增价跌、量缩价升、量缩价跌、天量天价、地量地价、放量突破、缩量回调、量价背离 |
| 均线系统 | 金叉死叉、多头排列、均线支撑压力、葛兰碧八法 |
| 技术指标 | MACD、KDJ、RSI、BOLL、OBV |

**`detect_rule` 是整个模块的支点。** 只有当形态能被算法量化识别，才能做到两件事：

1. 作答后精确揭晓「这里到底出现了什么」，并定位到具体是哪几根 K 线；
2. 长期统计每个形态的**真实胜率**（见 12.7）。

> 原设计里还有第三件事——「作答前构造方向配平的干扰项」。
> 作答前不再展示知识点后，这条**已废弃**。

建议 `detect_rule` 用内部的 **JSON DSL** 描述，便于维护和批量调参。

不可量化的知识点（如「道氏理论」）标记 `detect_rule = null`，
只在知识库中可查，不参与自动匹配。

### 12.7 杀手锏：用自己的数据统计每个知识点的真实表现

这是我们相对教科书的**独有优势**——手上就有全 A 股 30 年数据。
可以对每个可量化的知识点做全样本回测，产出类似这样的结果：

> **早晨之星** · 历史出现 12,847 次
> 之后 20 个交易日：上涨概率 54.2%，平均收益 +1.3%，中位数 +0.6%，
> 跑赢沪深300 的概率 51.1%

这能直接回答「这个形态到底有没有用」，把技术分析从玄学变成可以验证的命题。
数据积累后还能按板块、按市场环境（牛 / 熊 / 震荡）分组统计。

**三条统计纪律：**

1. 必须用**全样本**，不能用用户练过的题算（样本小，且用户会选择性记忆）。
2. 必须**包含退市股**，否则又是幸存者偏差。
3. 必须给出**样本量**。样本不足 100 次的知识点标注「数据不足」，不展示胜率。

### 12.8 数据模型与性能

| 表 | 层 | 说明 |
|---|---|---|
| `dim_knowledge` | clean | 知识点定义（见 12.6） |
| `fact_knowledge_match` | app | 匹配结果：`match_id, kb_id, code, start_date, end_date, confidence, severity_score, detail(json)`，索引 `(code, date)` / `(kb_id)` |

**计算策略：**

| 场景 | 策略 | 理由 |
|---|---|---|
| 用户**下单后**的区间匹配 | **按需算** | 单区间数据量极小，毫秒级；且必须等用户提交**下单**后才能跑 |
| 全历史形态位置（支撑 12.7 的胜率统计） | **预计算落库** | 结果复用度高，算一次用很久 |

**性能量级估算**：全历史约 4500 万行，按 code 分区做向量化计算
（用 DuckDB / Pandas，**绝不要逐行 Python**）。单形态全市场约数秒到数十秒，
30 个形态合计约 10~30 分钟单核，多进程可压到 5~10 分钟。
匹配结果保守估约 3000 万行，Parquet 压缩后 **300~600 MB**。

**关键设计：两条路复用同一套 detector 纯函数。**

- 用户区间匹配 = 对子区间调用 detector
- 全历史统计 = 全量跑 detector + 在命中点上接「未来 20 日收益」

零重复实现，也就不会出现「展示用的规则和统计用的规则不是同一个」这类最难查的 bug。

### 12.9 开关设计：两级

用户要求支持关闭 / 开启。修订后只需两级：

| 层级 | 控制内容 |
|---|---|
| **总开关** | 知识复盘模块 开 / 关 |
| **子开关** | 作答后知识点提示 开 / 关 |
| **模式预设** | 学习模式（全开，默认） / 纯净模式（全关） |

原设计的三级开关和四种模式**已收敛**——作答前不再展示任何内容，
「作答前提示」这个开关**失去了控制对象**。

另外保留一个**速查入口**：不进练习、直接翻知识库，按分类浏览与搜索。
它是知识库的浏览界面，不属于练习流程。

### 12.10 开关状态只用于学习统计，不再做成绩分账

原设计要求把 `knowledge_mode` 计入作答快照、并按开关状态**分账统计成绩**。
修订后这个结论要**降级**：

**为什么**：分账的初衷是防止「开着作答前提示答对」的虚高成绩污染纯净成绩。
但现在作答前本来就不给任何提示，**开关不影响作答难度**，也就没有分账的必要。

**改为**：`fact_order` 仍记录 `knowledge_mode` 和「下单后是否查看了知识点」，
但用途变成**学习行为统计**——例如「复盘查看率」、「看过某知识点的题目，
后续同类题目的判断准确率是否提升」。

这是衡量学习效果的有用指标，而不是难度校准指标。

### 12.11 知识库内容：全覆盖，由 AI 长程整理

用户决策：**知识点要齐全**，这件事可以作为一个独立的长程任务持续做，
系统设计只需**预留好新增空间**。

| 项 | 决策 |
|---|---|
| 覆盖范围 | **不设数量上限**，按知识体系完整梳理，而非只挑几十种 |
| 建设方式 | 由 AI 分批整理成结构化条目（含 `detect_rule`），持续追加 |
| 系统要求 | 新增知识点**不需要改引擎代码**——知识点是数据，不是代码 |
| 建设节奏 | 独立任务线，与开发解耦，互不阻塞 |

**工程上的三个前提**（决定"新增空间"是否真的留出来了）：

1. `detect_rule` 必须是**数据**（JSON DSL），不能是写死的函数。
   新增一个知识点 = 插一行数据，不是改一行代码。
2. 引擎只认 DSL 定义好的**原语**（特征比较、逻辑组合、时序关系）。
   遇到表达不了的新形态 → **扩展原语**，而不是给单个知识点写特例代码。
   这条纪律一旦破了，引擎会迅速腐化成"一堆 if-else"。
3. 每个知识点带 `enabled` 开关与版本号，允许分批上线、灰度验证、出问题单独下架。

建设计划、完整分类体系与 DSL 规范见 `02-知识点库建设计划.md`。

### 12.12 匹配引擎技术路线：规则 + DSL

用户决策：**用规则匹配**（不引入需要训练数据的模型），LLM 只做预留。

**为什么不是模式识别 / 机器学习**

| 维度 | 规则匹配 ✅ | 模式识别 / ML |
|---|---|---|
| 需要训练数据 | **不需要** | 需要大量人工标注，成本往往比写规则还高 |
| 可解释性 | **每次命中都能说清"为什么算命中"** | 黑箱，无法向用户解释 |
| 调参方式 | 改 DSL 参数，立即生效 | 重训模型 |
| 上线速度 | 写完一条规则就能用一条 | 要凑齐数据集才能开始 |
| 新增形态 | 加一条数据 | 往往要重新标注 + 重训 |
| 覆盖广度 | 只能识别**预先定义好**的形态 | 能发现未定义的模式 |

对学习平台而言，**可解释性是刚需**——用户必须知道「为什么这段算早晨之星」，
否则知识点起不到巩固记忆的作用。所以规则匹配在这里不是妥协，是正确选择。

**取舍的自觉**：规则匹配的已知短板是"只能识别预先定义好的形态"。
这个短板由 V2 的模式识别**补充**（用于发现规则没覆盖到的模式），而不是**替换**规则。

**DSL 规范与完整示例见 `02-知识点库建设计划.md`。**

## 13. 部署形态与安全

用户决策：**软件做成 Web UI，支持部署到 Linux 云服务器，并配备认证登录防止攻击。**

这是相对「本地单机工具」的一次定位升级，影响面比看起来大。

### 13.1 形态收敛

| 项 | 结论 |
|---|---|
| 前端 | **Web UI**（浏览器访问）。不做桌面客户端，不做移动端原生 App |
| 后端 | 常驻 API 服务，负责数据查询、结算、知识点匹配 |
| 部署 | 可部署到 Linux 云服务器；本地开发环境同样跑得起来 |
| 访问控制 | **必须认证登录**。虽然是单用户，但默认假定端口暴露在公网 |
| 传输 | 强制 HTTPS |

### 13.2 安全基线（公网暴露，这些不是可选项）

| 项 | 要求 |
|---|---|
| 认证 | 登录鉴权；密码不存明文（用慢哈希）；会话有有效期 |
| 暴力破解防护 | 登录失败限速 + 临时锁定 |
| 传输加密 | 全站 HTTPS，禁止明文回退 |
| 请求防护 | CSRF 防护、CSP、收敛常见 Web 攻击面 |
| 数据库访问 | 参数化查询，**禁止拼接 SQL** |
| 暴露面收敛 | 除 Web 端口外不对外开放其他端口；数据文件不做静态目录暴露 |
| 备份 | 数据与配置可备份、可恢复 |

> 单用户 ≠ 低风险。公网 IP 上的服务会被持续扫描，**认证是必要项，不是加分项。**

### 13.3 对已有决策的冲击

| 原决策 | 影响 |
|---|---|
| 存储用 DuckDB（单机嵌入） | **仍然适用**。单用户 Web 服务同进程访问 DuckDB 没问题。但必须明确**单写者约束**：数据同步任务与 API 服务不能同时写 |
| 可移植性「拷贝文件夹即可运行」 | 改为「**本地可跑 + 可部署 Linux 服务器**」两条路径都要成立 |
| 数据放在本机 | 改为数据**放在服务器**；本地开发用同一套代码指向不同数据目录 |
| 每日同步在本地执行 | 改为在**服务器**上跑定时任务（注意服务器时区） |

### 13.4 待确认的技术细节

1. **服务器时区**：定时任务按北京时间 16:00 触发，必须**显式指定时区**。
   服务器若为 UTC，会错 8 小时——这类 bug 通常要等到"某天数据没更新"才被发现。
2. **数据在哪拉**：Baostock 从服务器直接拉，还是本地拉完上传？
   建议**直接在服务器拉**（省一次搬运，服务器网络通常更稳）。
3. **DuckDB 单写者约束**：同步任务写入时需与 API 服务协调（错峰执行或加文件锁）。
4. **Baostock 实际更新时间需实测**：用户定的 16:00 是 A 股收盘（15:00）之后，
   但 Baostock 是盘后更新，**具体几点更新完需要实测确认**。
   若 16:00 时当日数据尚未就绪，同步任务会拉不到当天数据——需要调整时间或加重试。

## 14. AI 接入

用户决策：**暂时用 DeepSeek，预留扩展。**

### 14.1 必须有供应商抽象层

不能把 SDK 调用散落在业务代码里。要求：

```
LLMProvider（接口）
├── chat(messages, output_schema) -> dict    结构化输出
├── 能力声明：JSON schema 支持 / 上下文长度 / 是否可流式
└── 实现：DeepSeekProvider（首个）；后续可加其他实现

调用方只依赖接口，不依赖具体供应商。
```

切换供应商 = 换一个实现 + 改配置，**业务代码零改动**。

### 14.2 AI 的职责边界（重要）

AI 只做三件事，**全都不涉及数值计算**：

| 职责 | 说明 |
|---|---|
| 挑选与叙述 | 从算法切好的候选区间池里挑题、写题目描述与考察点 |
| 归因解读 | 结算后解释「为什么这笔交易亏了」。**只解读数字，不重算数字** |
| 知识库整理 | 长程任务：把知识点整理成结构化条目（含 `detect_rule`） |

**绝不交给 AI 的事**：区间边界、收益率计算、结算结果、判断对错。
数字必须由算法算——这既是准确性要求，也是防前视的要求。

### 14.3 已知风险与对策

| 风险 | 对策 |
|---|---|
| 模型侧前视（训练语料含该段行情） | 输入脱敏：不含真实日期与股票名，只给编号与时间偏移 |
| 幻觉（编造数字） | 结构化输出 + 字段校验，缺字段即丢弃；AI 只叙述不计算 |
| 供应商锁定 | 接口抽象（见 14.1） |
| 成本失控 | 批量预处理优先；知识库整理走批处理而非按需触发 |

## 15. 时间回放模式

用户决策：**把时间推回到某一天，让用户在那一天去买股票，用户自己推进时间。**

这是产品的第二个训练模式，与原有「区间判断模式」并列。
**完整设计见 `03-时间回放模式设计.md`**，本节只记决策要点。

### 15.1 双模式对照

| | 判断模式 | 回放模式 |
|---|---|---|
| 时间形态 | 一次性给一段区间 | 逐格推进，像真实看盘 |
| 交互 | 三选一 | 买 / 卖 / 加仓 / 减仓 |
| 仓位 | 无（虚拟） | **有真实仓位** |
| 结果 | 单次收益率 + 机会成本 | 账户净值曲线 + 交易明细 |
| 训练目标 | 单次决策质量 | 买入时机、仓位管理、盘感 |

**额外收获**：判断模式里「买入 / 持有 / 卖出」在无仓位前提下语义重叠的老问题，
在回放模式中因有真实仓位而**自然消解**。

### 15.2 五条硬约束

1. **只能前进，不能后退。** 服务端只提供 `advance(n)`，不提供 `set_time(t)`。
   能后退等于能反悔，模式立刻失去意义。
2. **粒度默认 5 分钟。** 因为 Baostock 有 5 分钟线（1999 年至今）但**没有 1 分钟线**。
3. **成交价用下一格。** 在第 N 格下单，用第 N+1 格成交。
   用当格收盘价成交等于让用户「买在最低点」，是**分钟级的前视偏差**。
4. **可见性边界与判断模式一致。** 所有数据只返回 `dt <= current_dt`。
5. **单股票零预处理。** 一只票 10 年分钟数据仅约 12 万行，选定后即时加载；
   只有全股票模式才需要预下载（10 年约 7.2 亿行）。

### 15.3 对已有决策的影响

| 原决策 | 影响 |
|---|---|
| 数据源只需日线 | **须增加分钟线**（Baostock 5/15/30/60 分钟，1999 年至今） |
| 数据同步时间 16:00 | **改为 21:00**（日 K 17:30、分钟 K 20:30 才入库） |
| 数据规模 4500 万行 / < 1 GB | 回放模式需额外 **7.2 亿行 / 4~7 GB**（5 分钟线 10 年） |
| 结算逻辑 | 回放模式**不需要结算**——净值曲线本身就是结果 |
